# STARGATE 维护手册：修 bug、合并、测试、上线

> **当前状态（2026-10-15）：自动灰测和自动上线正在搭建，启用后删掉这一段。**
> - 启用前可以照常提 PR、跑 CI，但先不要合并，也不要手动部署。
> - 急需上线的，在群里找总控。

这份文件放在仓库 main 上，是管理员维护平台的唯一流程说明。流程一变，就在同一个 PR 里改这份文件，所以 main 上看到的永远是现行做法。开发规范见 [AGENTS.md](../AGENTS.md)，功能范围见 [FEATURES.md](FEATURES.md)，你用的 AI 代理（Claude、Codex）会自动读取 AGENTS.md。

## 一句话流程

**开分支改 → 提 PR → 灰测自动跑，变绿 → 自己合并 → 约 10 分钟后自动上线 → 出问题就点 Revert。**

不需要找人审批，也不需要登录服务器。

## 1. 谁能做

- 仓库 Jarv1sP/stargate 的协作者（Write 权限）。现在有：Jarv1sP、javis6497、pengliangliu、halashaor、yedique。
- 加人、去人由 Jarv1sP 在 GitHub 设置里操作。名单只有这一份。

## 2. 改代码

1. 从最新 main 拉分支，取名 `fix/简短描述` 或 `feat/简短描述`。不能直接推 main（分支保护会拒绝）。
2. 改之前读 AGENTS.md 和 FEATURES.md。清单外的功能不加，已删除的功能不加回来。
3. 一个 PR 只做一件事。修 bug 必须带一条测试：没修之前它失败，修好之后它通过。
4. 本地先跑通：`npm test`、`npm run test:ui`、`npm run test:python`、`git diff --check`。环境要求见 AGENTS.md §八。
5. 提 PR，写清三件事：什么问题、怎么修的、怎么测的。

## 3. 防屎山：硬规定

违反下面任何一条，PR 一律退回，灰测绿了也不行。每条的原因写在 AGENTS.md 对应章节。

1. **不加检查**：不加 SHA、指纹、证明、回执、重复比对、多轮确认，也不加“多一个字段就拒绝”的严格校验。只允许五类：登录、系统盘隔离、回收站、完整性四样、资源底线。（§二 §四 §五）
2. **只改要改的**：不顺手重构、不顺手改名、不顺手加功能。超过 800 行的文件只改必要处，要拆分先提方案。（§一）
3. **删干净**：删功能时，代码、测试、文档、配置一起删。不留兼容层、旧入口、开关、注释掉的代码和死代码。（§八 §九）
4. **不新造轮子**：先找现有函数和组件复用，不写第二份实现。不新增后台服务、守护进程、缓存层或新依赖，确实需要时先提出来。
5. **不留生成物和私货**：build/ 等构建产物不进仓库；不提交凭据、.env、真实地址、主机指纹、生产数据或截图。（§十）
6. **报错说人话**：用户看到的报错要讲清原因和下一步，不用术语。未知就显示未知，不画成 0、空闲或成功。（§五 §六）
7. **文档只写现状**：改了行为，就在同一个 PR 里改对应文档；不写历史，不写“以前是怎样”。（§十）
8. **测试只守现存行为**：删掉的检查，连同它的测试一起删；不为凑通过去改断言。（§八）
9. **重要决定先说**：改协议、删功能、改权限、改发布流程，先在 issue 或群里提出，由 Jarv1sP 或总控确认后再做。（§九）

## 4. 测试：灰测

- 每个 PR 和每次合并到 main，都会在 GitHub Actions 上自动跑灰测（检查名 `gray`）。它在隔离环境里把门户、模拟节点、CLI 和网页从头搭一遍，把主要功能全跑一遍，大约半小时（启用后按实测时间更新）。
- 结果显示在 PR 底部。点 Details 能看每一步；失败的话，在 Summary 里下载 `summary.md` 和日志。
- 灰测红了就不能合并，这一条由 GitHub 自动拦。修好后推新提交，灰测会自动重跑。
- 灰测测不到：真 GPU、外网、Windows 真机、校园网直连。改到这些地方，PR 里写明你是怎么手工验证的。
- 灰测本身有 bug 时，单独提 PR 修灰测，不要为了让自己的 PR 变绿去改灰测。

## 5. 合并

- 灰测变绿后，作者自己点 **Squash and merge**，不需要别人批准。改动大或拿不准的，在 PR 里 @ 一位管理员看一眼。
- 改动会动用户数据（迁移、批量改删）时，在 PR 标题前加 **【手动】**。这种 PR 合并后不会自动上线，由 Jarv1sP 或总控在维护时段手动上线，只有这类才开维护模式。

## 6. 上线（自动）

合并到 main 后，GitHub Actions 依次自动执行：

1. 在 main 上再跑一遍灰测。
2. 构建门户镜像。
3. 上线：
   - 门户：用户不会断线，切换时请求排队等几秒。新门户起不来就继续用旧的。
   - CLI：随门户一起更新。
   - 节点：只有改了 `node/` 或 `gpuq/` 才更新。四台逐台安装，前一台正常了才装下一台。正在跑的任务不受影响。

上线进度和结果在两个地方看：
- 仓库的 **Actions**，看这次运行里的 `deploy` 一步；
- 仓库首页右侧的 **Environments → production**，每次上线是谁合并的、哪个提交、成功没有，都记在这里。

**上线失败时**，线上保持上一版不动。看 deploy 日志修好后，再提 PR。

## 7. 出问题怎么办

1. **先恢复，再修。** 在 GitHub 上打开出问题的那个 PR，点 **Revert**，生成回退 PR。灰测绿了就合并，它会自动上线上一版。
2. 再开新 PR 慢慢修。
3. 平台整体挂掉、连 Revert 都上不去时，可以 SSH 上服务器应急处理。处理完必须补一个 PR，把手改的内容写进仓库，并在群里说一声。不允许把服务器上的手改留着不管。

## 8. 不能做的

- 直接推 main、关掉分支保护、绕过或跳过灰测。
- 改 `.github/workflows/` 里的灰测或上线流程。要改先提出来，由 Jarv1sP 或总控处理。
- 平时直接在服务器上改代码、装包、改配置。只有第 7 节的应急可以，而且事后要补 PR。
- 提交凭据、密钥、真实地址或生产数据。仓库是公开的。

## 9. 这份文件怎么维护

- 流程、规则一变，就在同一个 PR 里改这份文件和 AGENTS.md。
- 发现写的和实际不符，直接提 PR 改，或在群里说一声。
